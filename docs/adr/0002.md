# ADR 0002 · Tenant isolation with forced PostgreSQL row-level security

**Status:** Accepted

## Context

A multi-tenant security platform holds the most sensitive data a customer has. An application bug must not be able to return another tenant's rows.

## Options considered

1. Database per tenant
2. Schema per tenant
3. Shared tables with a tenant column checked in application code
4. Shared tables with forced row-level security under a role without BYPASSRLS

## Decision

Every tenant table carries tenant_id and is protected by FORCE ROW LEVEL SECURITY. The API connects as a role that cannot bypass it and sets the tenant per transaction from the validated identity only; tenant headers are ignored.

## Consequences

- Isolation holds even if a query in the application forgets a filter.
- Cross-tenant isolation tests run against a real PostgreSQL on every build, including every new table.
- Platform-wide operations use a separate administrative role and are audited.
