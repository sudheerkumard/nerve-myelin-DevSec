# ADR 0001 · One finding schema with fingerprints

**Status:** Accepted

## Context

Fifteen engines and many imported scanners report the same weakness in different shapes. Separate queues per tool mean duplicate tickets, inconsistent severity and no single answer to 'what do we fix first'.

## Options considered

1. Keep each tool's own record and link them in a correlation layer
2. Normalise everything into one record and de-duplicate by a fingerprint

## Decision

Every result is normalised into one finding record. A fingerprint built from engine, rule, CVE, package, file, line and repository identifies the same weakness across scans and tools; the finding ID is derived from it.

## Consequences

- Policy, gates, ticketing, reports and dashboards work the same for every engine, including cloud accounts and clusters.
- A finding closes only when the engine that found it ran again and no longer reports it; imports never close other findings.
- Changing the fingerprint inputs is a breaking change and needs a migration of stored fingerprints.
