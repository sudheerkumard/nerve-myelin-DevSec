01

The front door has moved

For the first time in the 19 years of the Verizon Data Breach Investigations Report, exploiting a software vulnerability is the most common way attackers get in. The software delivery chain is now the attack surface.

31%of breaches start with an exploited vulnerability, ahead of stolen credentials [1]
48%of breaches involve a third party, after a 60% rise in one year [1]
$4.99Maverage cost of a breach, the highest on record [2]
24 hto warn EU authorities of an actively exploited vulnerability [3]

Two trends moving the wrong way

Share of breaches, by edition of the Verizon DBIR

Exploited vulnerability as initial accessThird party involved

Sources: Verizon DBIR 2024, 2025 and 2026 [1].

What changed

Attackers now use AI to cut the time from a published vulnerability to a working exploit from months to hours [1]. A vulnerable dependency, a leaked pipeline token or a misconfigured cloud account is reachable long before a quarterly scan or an annual penetration test would find it.

At the same time, more of every application is built from other people's code: open-source packages, build actions, container images and AI models. Each one is a door, and each belongs to a supplier.

The question for leadership is no longer whether to secure the delivery chain, but whether it can be shown to be secure.

Cost and accountability

The cost lands on the business, and the accountability on the board

Average cost of a breach (USD millions)

IBM and Ponemon Institute, Cost of a Data Breach Report 2024–2026 [2].

Costs rose 12% in a year, driven by detection, escalation and lost business. The same research finds that organisations using security AI and automation extensively cut breach costs by almost USD 2 million [2]. Automation is now a financial lever.

The regulatory clock

NIS2 adds the same direction of travel for essential and important entities: management bodies approve and oversee cybersecurity measures, must be trained, and can be held liable [5].

Why point tools fall short

Most organisations protect each stage of delivery with its own tool, its own severity scale and its own dashboard. Each sees one stage. None can tell the board where the organisation stands.

Code

Injection, weak crypto

Dependencies

Vulnerable or malicious packages

Secrets

Tokens in source and pipelines

Infrastructure

Public storage, open ports

CI pipeline

Script injection, token theft

CD / GitOps

Unreviewed production deploys

Running APIs

Broken authorisation

AI components

Prompt injection, unpinned models

Cloud accounts

Over-privileged identities

Workloads

Attackers already active

Ten stages. Ten tools. Ten different answers to "how exposed are we?"

The result is predictable. Security teams triage thousands of alerts that describe the same problem in different words. Engineering receives tickets it cannot prioritise. Releases go out because nothing joined the dots between a vulnerable package, the pipeline that built it and the cloud identity it runs as.

And when the board asks whether the organisation is getting safer, the answer is assembled by hand, from screenshots, the night before the meeting.

Alert fatigue
The same weakness reported by several tools, each with its own severity
Blind spots
Nobody sees the path from a code flaw to a cloud admin right
No proof
Reporting is manual, so it is late, partial and hard to audit

How it works

A stateless API, a single policy engine and tenant-isolated storage, deployable as SaaS, single-tenant, on-premises or fully air-gapped.

Scales out

Stateless API behind a bounded scan queue; add replicas as load grows.

Isolated tenants

PostgreSQL forced row-level security: one tenant cannot read another, even through a bug.

Secrets in the vault

Source, ticketing and cloud credentials live in the vault, never in the database or reports.

Code stays home

Scans run on your runner. Findings are uploaded; source code is not.

Data flow

From a commit to a decision in eight steps

Every step is recorded, so the path from a developer's change to a release decision, a ticket and a closed finding can be shown to an auditor.

What leaves your network

  • Findings, the SBOM and the policy decision
  • Cloud configuration metadata, read-only, never data or Kubernetes Secrets
  • Runtime detections, with tokens and passwords redacted before storage

What never does

  • Source code: it is read where the scan runs
  • Secret values: detected secrets are fingerprinted, not stored
  • Anything at all in air-gapped mode, where advisories are carried in offline

From finding to fix

Severity alone does not say what to fix first. A critical issue in a test fixture matters less than a high one that is exploited in the wild and reachable from the internet.

P0
Immediate
Fix within 2 days
P1
Urgent
Fix within 7 days
P2
Planned
Fix within 30 days
P3
Routine
Fix within 90 days

Aligned with CISA SSVC

Every finding is placed on the CISA decision tree (Track, Track*, Attend, Act) using exploitation, automatability, technical impact and mission impact [6]. The decision points are shown, so an analyst can see and challenge them, and they are recomputed when intelligence changes.

Noise removed before anyone looks

  • Results describing the same problem are merged
  • Test, fixture and vendored code is de-prioritised
  • Suppressions need a reason and are audited
  • Accepted risks must expire

Release gate and closed loop

Unsafe code does not ship. Fixed code closes itself.

Commit

Developer pushes a change

›

Scan

Fifteen engines on your runner

›

Decide

One policy: pass, warn or block

›

Gate

Exact commit checked at deploy

›
Deploy
Passed policy
Blocked
Owner told why

Fails closed

A commit that was never scanned, or scanned without a required engine, is blocked.

Only what is new

With --scope new, only findings a commit introduced can block, so old debt does not stall releases.

Governed exceptions

Time-boxed, exactly scoped, approved by someone other than the requester, with MFA.

The closed loop

Assign
Routed ticket, one per finding
Fix
Upgrade plan or AutoFix pull request
Verify
Re-scan closes it automatically
Prove
Report, SBOM, VEX and audit trail

Works with GitHub Actions, Azure Pipelines, GitLab, Jenkins, Bitbucket and Argo CD, with tickets in Jira, ServiceNow and Azure Boards and alerts in Teams and Slack.

name: production
mode: enforce          # audit | warn | enforce
gates:
  - id: block-known-exploited
    when: { kev: true }
    action: block
  - id: block-critical-reachable
    when: { severity: [critical], reachable: true }
    action: block
  - id: block-secrets
    when: { engine: [secrets], severity: [critical, high] }
    action: block
  - id: block-mrs-80
    when: { mrs_gte: 80 }    # NERvvE Risk Score, P0
    action: block

One policy file, every stage

The same versioned policy decides pull requests, pipeline runs and deployments. It is approved by a second person, identified by its content, and runs in audit, warn or enforce mode, so teams can roll it out without stopping delivery.

06

Code to cloud to runtime

Configuration, identities and live detections are joined to the code that created them. When exposure, an exploitable weakness and privileged access meet on one workload, it is reported as a single attack path.

Cloud posture

67 checks across Azure, AWS and Google Cloud, by CIS section, collected read-only.

Kubernetes

25 checks: Pod Security, RBAC, exposure and isolation. Cannot read Secrets.

Identities

14 checks on effective privilege, MFA, key age, escalation and public access.

Runtime

Falco and Tetragon detections, grouped per workload, mapped to MITRE ATT&CK.

09

Trusted by design

A security platform must meet the standard it enforces. NERvvE DevSecOps is built, tested and released to the same policy it applies to your code.

Identity

OIDC single sign-on with Keycloak, Microsoft Entra ID or Okta; MFA and step-up

Authorisation

Role-based permissions on every endpoint: viewer to tenant admin

Tenant isolation

PostgreSQL forced row-level security; keys bound to one tenant

Secrets

Credentials in the vault; nothing secret in reports or logs

Audit

Append-only, hash-chained audit trail exportable to any SIEM

Network

Server-side request forgery guard on every outbound call

Supply chain

Pinned dependencies, its own SBOM, scanned by itself before release

Honest limits

Evidence and location on every finding; every triage decision reversible

Air-gapped ready

Runs with no internet; advisories carried in offline

Deploy it your way
Multi-tenant SaaS
Fastest start, regional hosting
Dedicated single-tenant
Isolated infrastructure for regulated organisations
On-premises
Docker Compose or Helm on Kubernetes, inside your network
Air-gapped
No internet access; offline intelligence packs

Framework mappings are evidence aids: they show where automated testing bears on a control and are not a certification. A labelled benchmark of vulnerable and safe code runs on every change; precision and recall must not regress.
